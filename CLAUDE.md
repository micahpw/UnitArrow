# UnitArrow — working notes for Claude Code

## What this is

UnitArrow carries physical units and quantity semantics on Apache Arrow
columns. A unit annotates a whole column as an Arrow extension type
(`unitarrow.quantity.v1`) via two field-metadata keys, so it survives IPC,
Flight, and Parquet with no sidecar files. Conversion is a metadata-level
scalar rescale, never a per-element object dispatch. A consumer that has
never heard of UnitArrow sees a plain typed column with legible metadata
beside it.

All parsing, normalization, dimension algebra, and factor computation live in
one Rust core (`unitarrow-core`), exposed to Python, TypeScript, and WASM
through thin bindings.

## Normative constraints

These four are the ones most likely to be eroded by a well-meaning change.
Treat them as invariants, not preferences.

### 1. §6.3 canonical form is the equality primitive

Cross-language equality and hashing depend on there being exactly one spelling
per unit expression. The rules (spec §6.3): resolve symbols through the
registry (aliases → canonical), merge repeated symbols by summing exponents,
drop zeros, then serialize as one `*`-joined product — positives first, then
negatives, each group sorted bytewise, signs inside exponents. **Canonical
form contains no `/`**: `W*K^-1*m^-2`, `MW*s^-1`, `s^-1`. Slashes and the
`1/s` form are input sugar only; exponent `1` is omitted; the empty product
is `"1"`.

- **Exactly one code path** in `unitarrow-core` produces canonical form.
  Bindings call it; they never re-derive it.
- **Never compare or hash a unit string that has not been through it.** A raw
  string from the wire is not a key.
- **Canonical form does not reduce to SI.** Spec §1 goal 4 is explicit: data is
  never silently canonicalized. `MW*h` and `MWh` are different canonical
  strings even though they are commensurable and numerically identical. Do not
  "helpfully" normalize to base units anywhere. See AMB-012.
- Writers MUST emit canonical form; readers MUST accept non-canonical input
  and normalize internally.

Canonical form and the §6.2 base-dimension vector are the two decisions M0
froze because they are the hardest to change later. Changing either is a spec
revision with a grammar or extension-name bump — never a refactor.

### 2. Conversion factors are exact rationals; floats come last

Registry `factor` and `offset` are `[numerator, denominator]` integer pairs
(spec §7.2). All composition — chaining, inverting, raising to an exponent —
is exact rational arithmetic.

- **No float literals in the registry.** No `1e6`, no `0.001`.
- **No `f64` intermediates in factor computation.** Convert to floating point
  only at the single final step where the factor is applied to data.
- This is what makes factors auditable and bit-identical across Rust, Python,
  and WASM. A float shortcut that "gives the same answer" defeats the entire
  point and will diverge on some binding.
- Watch for overflow: exponents multiply numerators and denominators fast.
  Reduce fractions eagerly; use a widening integer type rather than dropping to
  float.

### 3. §10 error codes are wire-stable identifiers

The taxonomy in spec §10 is a fixed vocabulary, identical across every binding:

```
E_UNIT_SYNTAX    E_UNKNOWN_UNIT    E_DIM_MISMATCH     E_UNIT_MISMATCH
E_AFFINE_COMPOUND  E_INTERVAL_MISUSE  E_BASE_MISSING   E_BASE_MISMATCH
E_CAST_LOSSY     E_BAD_PLACEMENT   E_KIND_UNSUMMABLE  E_TEMPORAL_MISMATCH
E_GRAMMAR_VERSION  E_BAD_METADATA  E_REGISTRY_INVALID
```

Warnings mirror the codes (`W_TAINT_INTRODUCED`, `W_COERCED`, …) — but the
warning taxonomy is not yet enumerated (AMB-045).

- Bindings map codes to native error types (Rust enum variant, Python
  exception class, JS error) but **preserve the code string verbatim**.
- Do not invent a code to cover a gap. One code is still missing: exponent
  overflow (`E_EXP_RANGE`, tracked as AMB-015). Adding a code is a spec
  change, and the conformance fixtures that depend on it stay `provisional`
  until it lands.
- Do not merge codes. `E_UNKNOWN_UNIT` (symbol does not resolve) and a parse
  failure are different conditions even though both reject a string.

### 4. §2 non-goals are the scope tie-breaker

The roadmap says this outright under "Risk watch": the spec's non-goals section
is the tie-breaker in every review. When a feature is arguably in scope, §2
decides against it.

- **No compute kernels, no plans.** Numeric execution belongs to arrow-rs,
  polars, DuckDB, JS. This project defines checking *rules* and exposes them as
  a type system. Plan serialization and lowering are the companion's.
- **No chart library.** Display stops at labels, formatted unit strings, and
  conversion factors.
- **No OWL / description-logic reasoning.** Vocabulary relationships are flat
  data resolved by lookup. There is no inference engine, ever.
- **No cross-currency conversion.** `USD/MWh` parses and propagates; exchange
  rates are time-varying data, not registry constants.
- **No per-element units.** One unit per column, always.
- **No per-row bases.** Per-unit (p.u.) columns require a column-uniform base.
- **No publishing or trust machinery.** Seals, derivation DAGs,
  reproducibility, advisories — all companion scope.

## Architecture rules (spec §4, normative)

1. **Bindings MUST NOT reimplement any `unitarrow-core` logic.** If a binding
   needs behavior, add it to core and call it. A parser in TypeScript is a bug
   regardless of how small.
2. **Core APIs are coarse-grained.** Submit a whole schema, receive all units,
   labels, dimensions, and factors in one call. Do not design chatty
   per-symbol APIs — every FFI and WASM crossing pays for them.
3. **arrow-rs stays out of the WASM build.** `unitarrow-wasm` depends on
   `unitarrow-core` only; arrow-js owns table handling in the browser. Browser
   execution uses the typed-array or SQL lowerings, never arrow-rs-in-WASM.
4. **`unitarrow-core` is `no_std`, requiring only `alloc`.** Not for size — that
   saving measured ~7 % — but so the constraint is compiler-enforced: the core
   cannot pick up a filesystem, clock, or thread by accident. `unitarrow-wasm`
   gates its allocator and panic handler on `cfg(target_arch = "wasm32")` so
   host builds still use std for tests and clippy.
4. **`unitarrow-py` has no required dependency on pyarrow, polars, or pandas.**
   All table I/O goes through the Arrow PyCapsule interface.
5. **Ontology constants are code-generated** from vocabulary files into plain
   Rust/Python/TypeScript modules, importable without instantiating a runtime.

## Conformance rule

Roadmap decomposition principle 4: **golden files land with the feature, never
after.** A binding is conformant when it passes the suite *without modification
to the golden files*.

So: if code disagrees with a fixture, the code is wrong until the spec says
otherwise. Editing a fixture to make an implementation pass is backwards — the
correct move is a spec change that updates the fixture first. Fixtures marked
`status: "provisional"` encode a recommended resolution to an open question and
are the one exception; they change when the corresponding AMB entry is decided.

## Distinctions that are easy to get wrong

- **Untagged is not dimensionless.** `"unit": "1"` is an explicit claim and is
  quiet. The *absence* of the extension is the absence of a claim, is contagious
  under arithmetic, and is loud inside opted-in checking contexts. Spec §5.3
  forbids a checker from suggesting `"1"` to silence a taint warning. `unknown`
  is a runtime taint state and is **never written to the wire**.
- **Affine is not delta.** `degC` is affine, non-composable, and invalid inside
  any compound expression (`E_AFFINE_COMPOUND`). `delta_degC` is purely
  multiplicative and freely composable. A quantity kind with `interval: true`
  MUST use the delta unit. This is the guard against a 20 °C swing converting
  to 68 °F instead of 36 °F.
- **`sum` is not `integrate`.** Summing a rate quantity across rows into its
  integral kind is `E_TEMPORAL_MISMATCH`, not a rounding concern. The only path
  from MW rows to MWh is an explicit, period-aware `integrate` on an `interval`
  column with a known period.
- **Mode is not a working-table property.** Modes (`strict` / `permissive` /
  `untracked`) are recorded at finalization. Working tables have no mode — which
  leaves reader behavior underspecified; see AMB-020.
- **Descriptions are prose, and prose goes stale.** `unitarrow:display_name`,
  `unitarrow:description`, and `unitarrow:references` (§5.5) are *plain* field
  and schema metadata keys, outside the extension blob — so §5.2's unknown-key
  preservation rule does not cover them, but the companion's data digest does.
  Dropping one breaks downstream seals (AMB-032). Descriptions MUST NOT be used
  for validation, and a derived column inherits no description: honest emptiness
  over stale prose. `publish()` lints metadata size — paragraphs, not documents.
- **Column digests localize; they never absolve.** Companion §5.4: intact
  column digests on a broken seal report *which* columns changed. They never
  upgrade the overall verdict — the signature is all-or-nothing.
